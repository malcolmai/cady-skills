# Agent host tasks, library and silent hosts

**Point:** Keep each agent's host task, skill library and silent-host handling exact, so scheduled agents keep running.

- **Scheduling:** Wake for a useful action or signal, not to keep an agent busy. The host schedules and executes; Cady runs no scheduler and holds the work, checkpoints and results. Only host readback establishes a configured recurrence, and only a reported result proves a run.
Every run of every agent follows the run sequence. Waiting work records its next action and due date and relies on the host's next wake; there is no separate wake mechanism. Dated reminders (renewals, notice deadlines, filings) are due items in company work, read by the bound agent through work_read, never a separate reminder, calendar file or schedule.
Cadence: Reuse the authorized cadence and actual host or spend limits; otherwise fit cadence to evidence freshness and deadlines without inventing a time quota. Actionable work continues until done or an actual limit; waiting work checks near the expected reply or deadline and backs off empty checks; with no ready work, stop the run and keep the next useful trigger. Coalesce or skip missed runs; never replay a backlog of external effects. Distinguish a finite task from a continuing responsibility. The Orchestrator wakes hourly as a baseline to keep work moving; the owner accepts it at setup (manage-agents step 7). Each tick is short workhorse-tier triage. Dispatch ready tasks (filed, unblocked, with doneWhen and the needed authority) in priority order; while one remains and limits allow, take it in the same run rather than waiting a tick. Start a new initiative or discretionary recurring work only when no ready task waits and usage has headroom (no host usage warning, rate limit or cost spike). With nothing ready, read what is due and exit. Where the host can reschedule, wake earlier for a known due date and stretch to at most daily while nothing is ready or usage runs hot, returning to the baseline when work appears. Waking more often than the accepted baseline is raising cadence. Learn of helper results from completion notices, not extra ticks.
Since your last pass: read cady_read changes {since: the time saved on your work item, important: false}, paging with its cursor; after a complete pass save this pass's start time, overlapping the boundary and deduplicating change ids. A change pointer is a reason to re-check, never a completion verdict.
Runtime: Choose the lightest capable runtime: a script for deterministic work, a supported native host schedule for periodic work, an always-on external agent only when response time justifies its cost and security burden. Verify the actual host's scheduler, persistence and tools before promising unattended work; local execution cannot run while the machine is off.
Host scheduler: the create result's install block names this host's scheduler and how to read it back. In Claude Code that is /schedule (a cloud routine, wake cloud_routine), a Claude Desktop scheduled task (desktop_task, the computer must be awake) or /loop in an open session (loop, ends with the session); Codex uses an automation or cron (cron). A host with no scheduler (Gemini CLI, Grok) cannot run the agent unattended: say so plainly, and use an OS cron only if the owner asks. Pass wake, task and checkedAt in host at bind.
Models: The host owns model and effort selection. Preserve explicit user settings and use supported host controls; when selection is unavailable, use the configured executor.
- **Library:** Install the company's roster, not the whole library: the library's install.py copies into the host's skills folder the company system (the Executive and the orchestrator) and the core skills on the first run, then each agent the Executive designed and the owner approved with `--add <agent>` (its role card, its function's skills and the skills the card lists from others); retire one with `--remove <agent>`. Preload each agent's role card in its agent file where the host supports it (Claude Code: the skills: list in .claude/agents/ preloads; it does not restrict the rest). Update with the host's update command: it pulls the library and resyncs the roster, replacing files the company has not edited and keeping edited ones with the new version beside them as <file>.upstream. Merge each .upstream by hand when the change helps, keeping the company's deliberate edits, then delete it; re-check affected agents, bind what you install and record the verdict (taken, partly or skipped, and why) in the work result. If the company keeps a fork, install from it instead, and once a month compare its baseline tag with the latest cady-skills release; if newer, read its CHANGELOG.md, merge what helps by hand and rerun the update. Nothing merges automatically.
- **Silent hosts:** A silent host's agents. Look at your other hosts at most once a day (agents_read: each host's lastContactAt and, for a host silent 72 hours or more, each live agent's moveTo). A host in contact: skip its agents unless you detect and confirm a severe risk (for example an agent sending out poor content); then pause that agent first and tell the owner. A silent host's agent: if moveTo.here is true, move it here (agents_set host {action: move}, agentId, expectedRevision), set up its host task at its stored cadence, read it back (agents_set host {action: bind, task, checkedAt, wake}) in the same run, and tell the owner in one line; if moveTo is another host, skip it; if moveTo is null, pause it (agents_set status paused with a note) and raise one ask to its owner to pause or retire (moveWhy says why). The server takes a move only from the host moveTo names, which is the target host's orchestrator; in the web app the owner moves an agent. Retire only an obsolete agent.
