# Selected company delivery

Carry one selected build or launch to an inspected result. Use when: a decided cross-functional delivery needs checks and owner readback. Not for: deciding scope (use `cady-product-method`).

## Selected delivery

- **Check:** Check the final result against the company's named critical paths, user journey and failure states; a poor flow fails acceptance. Distinguish known test-infrastructure failures from product failures with evidence. Use small deterministic checks for key edge cases; agent runs do not replace them. For a complex agent workflow, run one realistic, correctly scoped scenario covering several concerns; a fresh reviewer then checks its output and full transcript against each concern and the product's goal, and only then reads the agent's self-grade. A concern the run did not exercise stays unchecked. Per change, run the deterministic checks it touches; run the realistic end-to-end scenario once, on the final shape, and rerun a scenario only where a later change touches its concerns, and run independent scenarios in parallel within memory. Start confidence-threshold and broad edge-case campaigns only after the base case runs well; prefer reasoning and prior research to A/B tests. Label simulated, syntax-only, rendered, functional and independently reviewed evidence distinctly. Repair material defects and rerun affected checks after the last relevant change. Do not call a generated screenshot visually inspected or a syntax exit a functional test. A claimed helper or passing command is not proof of review or quality.
- **Handoff:** Read back the exact task and affected domain owner after checking the final artifact and before marking the selected task complete. For Product work, include the supported outcome, artifact and remaining evidence in the existing result. Do not imply a Product owner transition from a completed work item. Record the artifact/system reference, achieved outcome, limitations, review posture and unresolved work in the existing result; name checks actually run against the final artifact and state unrun or unobserved checks plainly. Carry forward the existing owner binding needed for continuation, including the operation's known subject and destination, rather than reconstructing it from names or narrative. Preserve the selected responsibility and task with their known revisions, applicable exact strategy/group revisions, owner result and material decision/artifact source references, logical-operation key and pending next action. Missing bindings remain unknown. An unrelated preferred role does not replace the selected assignment. Compare these material values and roles with owner/source readbacks; a strategy revision alone does not verify task or responsibility revisions. Typed delivery is host-reported. A go means ready to release; only the release owner records released with a receipt verifying the deployed artifact and target. Distinguish released from customer-validated. Reconcile uncertain effects before retrying and never widen external authority from task selection. For managed work, use existing claim and recovery fences, transition_company_work action='report_result' for a reviewable result, and action='accept_result' only through its authorized owner; a completed run or task report is not accepted work or business success. A cross-host handoff delivers the exact task and evidence, not permission to rebind a managed task or migrate an agent. If no allowed transition exists, retain an exact actionable handoff and continue safe work.
- **Plan:** Size each release as a usable customer tool: a narrow MVP on cheap infrastructure, with the research and architecture to reach best in class. When the open question is whether an idea is worth building, propose a small concept demo instead and label it a demo. Do not release intermediate steps nobody can use. Match planning effort to uncertainty and consequence. Reuse sufficient current research; a clear correction can proceed directly. Resolve material scope ambiguity against the applicable domain outcome and approved direction with bounded stronger-model advice or the reserved owner decision before dependent work. Plan the lowest catching checks with the work, consolidate acceptance fixes, and stop once acceptance is proved; broaden or repeat only for changed behavior, new failures or unresolved concerns. Preserve applicable acceptance and quality thresholds. For Product work where quality levers could change the build decision, reuse or prepare only the relevant profile levers with source, bar, current state (or unknown) and feasibility; a narrow correction or non-Product task need not create a profile. Release thresholds cite applicable levers alongside correctness, authority and safety, user journey and design, and cost where relevant. Where build shape is open, run the cheap experiments that decide it first. Don't build a lever that cannot reach its bar; adopt, or label the release a demo. Estimate build, QA and review separately from observed agent latency and cost where available; do not infer an AI time quota from human effort. A release is a Projects work item, not a Product bet. On the company work checkpoint use productId when binding the work to a customer product, and include typed release {name, stage: planned|build|qa|released, buildBy, qaDays (0-60), thresholds (up to 6)}; dueDate is the release date. Read back the checkpoint.
- **Scope:** Use the exact selected Projects task: its statement, acceptance, nextAction, evidence refs and, when present, goalId, agentId, dependsOn and productId. Allocation is priority evidence, not task identity or effect authority; a direct one-off needs no invented allocation, goal or agent. Read immediate parent and dependencies when they change the next decision; use exact owner selectors and disclose missing, denied or stale coverage. This method applies to a broad deliverable in any business, not a first-product or software mandate. For an actual first company product and route to customers, also select company_launch. Load only the relevant domain method. Reuse a complete selected skill body already served rather than refetching it; one or two preparation reads is a usability target, never a cap on needed investigation.
- **Work:** Continue useful authorized work through the company's chosen systems and host-native tools until acceptance or a justified dependency wait. Keep independent work moving when a dependency or actual limit affects only another action; a Cady task is continuity, not a host runner or extra authority.
