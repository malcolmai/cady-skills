# Run reporting: close and report a run

**Point:** Close each run with one checked report ending on a ready next move, so owners act on results.

- **Shape:** The ordinary reporting action is one work_set call. The call carries id, status, result, evidenceRefs when available and next only when needed: one line, and when present the step the result enables; narrative goes in the result. A no-work execution is still a run, which the harness records; a one-off with nothing material to report creates neither a run nor a task. For a continuing responsibility, omit an unchanged no-change result item; ending this run never completes the responsibility. If a linked material result changes the goal's supported summary or next action, reconcile that goal through its current owner and verify the next context; unchanged wakes and completed-task counts do not establish goal progress. Never record the run yourself: the harness records it (cady sync) with its times and outcome; usage stays with the synced execution. Point to the owner artifact by evidence ref; never duplicate its body in report metadata.
- **Recovery:** Retain the unchanged payload and stable partKey after a lost response; let the tool fill omitted request ids. A corrected payload gets a new report identity; never refresh a revision to force stale intent. Preserve material checkpoints, partial/blocked status and unresolved effects and follow the close tool's parts and pre-close checks during recovery.
- **Output:** Name the requested useful outcome in the task title, not a session or implementation step. First result sentence is the outcome title (what changed, short; the result field of work_set sets the rule) and states whether the requested outcome or only a named milestone is complete; put material remainder up front. A finish line names the deliverable, its size rule and what done is; a sample is labelled one and never meets a request for the deliverable; a budget, time-box or access stop closes as partial (delivered N of T). Done only when the requested finish line is met; a meaningful completed milestone stays partial on the same work (status open or blocked) with the remainder in result and the step that remains in next. Session end or intermediate deploy is not completion. A requested release includes applicable tests/QA and verified authorized release; research or drafting is done at the requested usable artifact. Then name each decision taken in the run (what, why in one line, and its ref), and end the report, and any reply to a person, on one ready next move: what to do first, with whom and with which message or artifact, as a recommendation the owner can accept or change. A research run's move is held for approval, never an unapproved send (preparing outreach is the channel's own work); propose more research only when it would change the call. Follow with concise checks/limitations and owner artifact or receipt refs. File only what someone will reopen to use or check: a deliverable, or source evidence no owner record holds. Do not file process notes, local transcripts or repeated company context. Use a review packet only when the owner must approve exact materials together; otherwise keep any necessary memo brief and action-led. Transcript review may diagnose retries, waste and tool misuse; persist only the material finding, its evidence ref and the correction in the existing owner.
- **Exceptions:** An offline_evaluation or spotcheck reports like any run: its result through work_set, citing requestId, scenarioId, repetition, configurationRef and the actual output or outputRef in evidenceRefs; the harness records the run. Do not add scheduled-slot or effect-receipt facts.
- **Close:** Work that changes what a person or host meets is complete only citing its done story walked blind at the installed build (story:<slug>#<step>@<run>), otherwise report it partial with next 'walk <slug> after release'. A reported result is otherwise taken as complete and corrected afterwards if wrong. A work item, when there is one someone would track (anyone), closes with its result; the harness records the run either way (agents only, every slot, even no_work). Deliver the requested result or verify the effect; preparation is progress unless requested. When the request is to prepare something for a person's review, the prepared, held item is the deliverable: report it done with the review ref. Link owner artifacts; never copy their body. Interactive runs end with the open asks (cady_read view work.needs_you); report nextRunAt for cadence or runsOn for trigger; when scheduledBy=none, name host setup and raise the owner ask. Batch the questions you turn into asks (`cady-company-decision` step 4). Notify a person only on failure, an owner action or a goal closed as met. For a stopped run, follow `agent-stop.md`. Your agent's privacy covers its runs, results, evaluations, cost, prompt and design only, never company work or decisions. Agents (agentId): nobody reads your reply, so your whole final reply is the reply line work_set returns.
