# System map (product map) and dimension maps

**Point:** Give people and agents one short, top-down map of a product: its point, its decisions and where a change goes.

- **Template:** System map format (the product map's format), the same for every product.
Levels: the product, its angles, each angle's key areas (two to five), the subjects (5 to 40 in all), a subject's parts, then the code it owns. These counts are a guide: the tool flags a map outside them and does not refuse it. A new product may start below them, and a key area may wait empty for a later release. Every node has a one-sentence point and may have bets; bets are not a level. The angles for software are Business logic (what it does), Interface (how people and agents reach it), Infrastructure (what it runs on) and QA (how we know it works); for a service or a physical product choose three or four that split it the same way, say so, and keep QA. A subject is something a person would change that has its own reason to exist. Core is what the product cannot run without: the records its logic is built on, and that logic; a module is a part that can be left out, such as a system of record of its own; a dimension is a part of how it is engineered (an Interface, Infrastructure or QA subject) that owns its code areas and, where a register exists (`engineering-cycle-dimensions.md`), a register row; a quality is not a subject (`quality-classes.md`). A subject sits in one key area, where a change to it is decided.
Bets: a bet is a choice that could have gone another way. Origin is owner (their words and hedges), inferred (what the code or a document implies, in your words, or a quoted statement whose author is unknown) or proposed (your own choice, with nothing in the sources behind it); source is where the wording came from, and a research pointer goes in the reason. Never invent a decision; a missing one is a question for the owner. One home per fact: decisions stay decisions, and the map cites them by subject.
The tool is two files, in this skill's folder or in the Cady skill library (github.com/malcolmai/cady-skills), under `assets/system-map`. `map.schema.json` names and explains every key of the source. `render_map.py` (Python, standard library only) checks a source against it and writes the map. If you cannot get the two files, stop and say so. Copy both into the folder `model` under the repository's `docs` folder, beside the source `model.json`. Use them as they are rather than writing your own renderer. A project's own key starts with `x_`, and a project's own render may add sections between or after the tool's. Running `render_map.py` writes `product-map.md` (the front page, then one card per subject; the file to publish) and `gaps.md` (the counts and the owner questions).
With a dimension register, a dimension's record carries its register ids and its one owner, and its first bet is the label (differentiating or not, with the reason); with none, omit them, and a missing label is an owner question.
An existing map in another shape moves to this format the next time it is restructured.
- **Sources:** What the map rests on: research on Technology and on Users, and an understanding of Assets. Each is owned elsewhere: prefer a pointer to restating it. Technology is a research concern: the technology research file (research/<title>.md, `cady-product-research`). Users (what problem are we really solving) is half product research (interview syntheses, `cady-product-customer-interview`, and the assumptions `cady-company-evidence` records) and half from GTM and the relationship manager (the persona profile, `cady-gtm-persona-profile`, and what customers said in their relationship records). Cite each as file:<id> in the reason of the bet it supports. Assets (what resources the company has) is an overall company understanding. What bears on the product, such as how much budget there is, comes in as a bet on the product: the limit, with a pointer to the company tree or the budget record. Outside a company record system, cite a repository document as file:<repo path>.
- **Build:** Building a map: the same steps for an existing product and a new one. Only the sources differ: an existing product's code and documents, or a new product's research and brief. For a new product write the map before the code, so each short iteration changes named subjects against a stated point. Before building, see the part "drafting" for whether a map exists. 1. Copy the tool beside the source (the part "template") and read before writing. Existing: the README and docs, the entry points, the top two levels of folders, the tests, CI, and any decision records or tracker. New: the Users research (for the point), the Technology research (for the technology bets), the limits from Assets and the brief (what the owner asked for). If the brief is not a file, save it beside the map and cite it as file:<repo path>. A sentence the owner wrote in it is an owner statement; it stays after clean-up. Copy owner statements word for word with where you found them; when authorship is unknown, quote them in the reason, mark the bet inferred and add one owner question asking which documents are the owner's own. 2. Product: its point and its bets. If the sources do not say whom it is for or what it beats, write your best reading and add an owner question. 3. Place the angles and their key areas, each with a point. 4. List the subjects and name the paths each owns. For a new product, name only the subjects the first release needs. Before the technology is chosen, name one folder per subject: a planned path is a plan, renamed when the code lands. 5. Releases. Existing: take them from the tracker or roadmap. New: give the first release a goal a user can reach end to end, and list its items in build order, with the paths each will create. 6. Complete `model.json` as the schema says, with the "sources" pointers that exist, run `render_map.py` and fix what it refuses. 7. Clean up (the part "clean_up"), then run the part "check". For a new product, then build the product one release at a time. After each release, render again, change a point or a bet only when a decision changed, and add the subjects the next release needs.
- **Clean up:** Cleaning up, at every build and every update of a map: always clean up if there is anything to clean up, including the codebase's existing documentation and the references to it, so there is one system, if that exists. Look for what the map now holds: architecture and overview documents, older maps, lists of folders, modules or decisions, and every reference to them (links in the README and in agent instructions, links between documents, comments and scripts that name them). For each one, remove it, or cut it down to what the map does not hold and point it at the map; then fix every reference to it. A document the map does not replace (a decision record, a runbook, an API reference, research) stays, in the paths of the subject it belongs to. Removing or rewriting a project's documents is a change to that project: make it as a change of its own, through that project's usual review (agent instruction files through their own change path), and list there what you removed, what now points at the map and what you kept, with the reason. Where you may not make that change, remove nothing: give the project's owner the list and ask them to make or approve it. When there is nothing to clean up, say so in the map's change.
- **Check:** Checking a map. On every change: `render_map.py --check` passes, and clean-up is done: no second copy of what the map holds is left, or the list of what remains is with the project's owner. On first generation and on a format change only: blind use. An agent that has seen neither the code nor the run that wrote the map gets only the map and three real changes (merged changes described without their paths; for a new product, items of the first release) and names for each the subject, the paths to read and what must stay true. The map passes when the answers match where the change landed or is planned; each miss is fixed in the map.
- **Drafting:** Drafting a system map. First find it: the File named <product's node path>/product-map.md (product/product-map.md, or product/<key>/product-map.md for one of several products), found with files_read mode find. If it exists, read it and update the map where it is edited instead of starting another. Otherwise find the one place it is edited from the host: the repo for software, else a Notion page or an HTML template you edit. Build it as the part "build" says, and review a new map or a larger change before merging, per cady-engineering-independent-review. Publish one Markdown File (export a Notion or HTML page to Markdown; Files takes no HTML) with `cady product map publish <path> --product <node path> --writer <URL of the place it is edited>`. The first run uploads the File under that name. Every later run, including the one whoever merges a map change runs from the merged source, adds a version of the same File and keeps that place. No decision names the map: its name is the pointer, and the File names where it is edited on its first line.
Keep the map true:
- Make each claim checkable and flag it when false, instead of prose no check reads.
- Mark anything to be removed with the work item that removes it, instead of a bare "to be removed" note.
- **Dimension maps:** Dimension maps. Save a map with files_set as a <slug>.logicmap.json File (format cady.logic-map.v1), then cite its file:<id> as evidence on the node it maps. For a product you build in code, add a development-loop or owner map when the product map leaves a consequential flow unclear.
