# Reporting a run

- **Close:** Work that changes what a person or host meets is complete only citing its done story walked blind at the installed build (story:<slug>#<step>@<run>), otherwise report it partial with next 'walk <slug> after release'. A reported result is otherwise taken as complete and corrected afterwards if wrong. Two records close a run: a run (agents only, every slot, even no_work) and a work item (anyone, only for an outcome someone would track). Deliver the requested result or verify the effect; preparation is progress unless requested. When the request is to prepare something for a person's review, the prepared, held item is the deliverable: report it done with the review ref. Link owner artifacts; never copy their body. Interactive runs end with the open asks (cady_read view work.needs_you); report nextRunAt for cadence or runsOn for trigger; when scheduledBy=none, name host setup and raise the owner ask. Batch the questions you turn into asks (`cady-company-decision-check` steps 2-3). Notify a person only on failure, an owner action or a goal closed as met. For a stopped run, follow `agent-stop.md`. Your agent's privacy covers its runs, results, evaluations, cost, prompt and design only, never company work or decisions.
- **Exceptions:** For offline_evaluation or spotcheck only, record through work_set with a `run` using the current schema retrieved through find_cady_tools (tool: work_set, detail: schema), then call_cady_tool. Preserve requestId, scenarioId, repetition, configurationRef, the Projects-derived evaluation runId, and actual output or outputRef; include only actually observed traces or usage in that schema. Evaluation reporting is exceptional and does not add a second ordinary run write. Do not add scheduled-slot or effect-receipt facts.
- **Output:** Name the requested useful outcome in the task title, not a session or implementation step. First result sentence is the outcome title (what changed, short; the result field of work_set sets the rule) and states whether the requested outcome or only a named milestone is complete; put material remainder up front. A finish line names the deliverable, its size rule and what done is; a sample is labelled one and never meets a request for the deliverable; a budget, time-box or access stop closes as partial (delivered N of T). Done only when the requested finish line is met; a meaningful completed milestone stays partial on the same work (status open or blocked) with the remainder in result and the step that remains in next. Session end or intermediate deploy is not completion. A requested release includes applicable tests/QA and verified authorized release; research or drafting is done at the requested usable artifact. Then name each decision taken in the run (what, why in one line, and its ref), and end the report, and any reply to a person, on one ready next move: what to do first, with whom and with which message or artifact, as a recommendation the owner can accept or change. A research run's move is held for approval, never an unapproved send (preparing outreach is the channel's own work); propose more research only when it would change the call. Follow with concise checks/limitations and owner artifact or receipt refs. File only what someone will reopen to use or check: a deliverable, or source evidence no owner record holds. Do not file process notes, local transcripts or repeated company context. Use a review packet only when the owner must approve exact materials together; otherwise keep any necessary memo brief and action-led. Transcript review may diagnose retries, waste and tool misuse; persist only the material finding, its evidence ref and the correction in the existing owner.
- **Recovery:** Retain the unchanged payload and stable partKey after a lost response; let the tool fill omitted request ids. A corrected payload gets a new report identity; never refresh a revision to force stale intent. Preserve material checkpoints, partial/blocked status and unresolved effects and follow the close tool's parts and pre-close checks during recovery.
- **Shape:** The ordinary reporting action is one work_set call. The call carries id, status, result, evidenceRefs when available and next only when needed: one line, and when present the step the result enables; narrative goes in the result. A no-work execution is still a run and includes its observed times; a one-off with nothing material to report creates neither a run nor a task. For a continuing responsibility, omit an unchanged no-change result item; ending this run never completes the responsibility. If a linked material result changes the goal's supported summary or next action, reconcile that goal through its current owner and verify the next context; unchanged wakes and completed-task counts do not establish goal progress. Do not separately record the same run. Manual and trigger runs derive runId from the close identity; omit it unless replaying a returned identity. skillsUsed accepts this method's published id from its Company context metadata and the execution.run_sequence alias. Run metadata is optional: through this same close call, include observed start/end times, usage or output only when the host actually observed them and the owner schema supports them; omit unavailable facts. Times omitted are recorded as the reporting time, not as execution timing. If the host provides no clock, register start at the beginning of the real attempt and finish when ending; these are attempt times, not effort duration. Never infer usage, execution start or skill use from a completion time or published version; identify only a skill version actually used. Point to the owner artifact by evidence ref; never duplicate its body in report metadata.
