# Agent design, setup, review and retirement

**Point:** Design, review and retire each agent as written, so every agent has a goal, a measure and an owner.

- **Agent design:** Design inputs: agent name and function; one goal; risk class; measure and its data (the target and readings live on the goal it serves); cadence or trigger, with why; approval limits; skills; owner member; first task, its checks and evaluation criteria; end or escalation condition.
Authority inputs: a verified member credential; host identity from the current Cady connection; expectedRevision null for a new agent or run, or the current revision for a change; current agentId for changes. decisionId and nonce are the server's: to retry, repeat the exact call.
Scope: one recurring agent per goal or sub-goal (decision product:company-model), normally one per function in use, with the role cards and skills it needs installed. Parallel sessions are runs of that agent, not new agents, and so are subagents doing its tasks. Split a child agent out only for a different risk class or grant, or a different cadence or host (the safety-isolation exceptions); parallel work alone is not a reason to split. A channel execution agent with its own sending account or grant may be split under this rule.
Responsibility: a cadence is set by duty, deadline and evidence freshness; a research agent's responsibility is named key questions (framed with the matching skill from the skill library); the function head keeps the decisions. Critical covers sending or publishing to non-members, spending or committing money, signing, filing, inviting or sharing data externally, changing external accounts or access, deleting owner records, or drafts released automatically by a grant, scheduled task or other agent.
First task and evaluation: one cycle of the real deliverable at its finish line; a standard agent's first task touches each tool the duty needs. Each brief.doneWhen line is a reader test (a yes/no question a reader without context can answer), tagged (check), (fresh) or (person) by who can verify it; brief.stopIf holds the limit that ends the run early (staying within limits is always one). Agent-level limits and assignment stay in limits and duties. Ask once for missing inputs, accounts, grants or scheduler; no secrets in chat.
Re-class and prepare-only test a new path on any grant, tool, access or trigger change. A goal link is priority evidence, not permission. For substantive drafting or adaptation, follow the matching writing-craft skill from the skill library and its conditional drafting reference; skip it for obvious corrections.
- **Agent setup:** Create: agents_set with the responsibility in duties, the installed skills, limits, and triggers: [] for on-demand or one schedule object or {kind:'event', on:'<description>'} in an array. A schedule is the cadence object itself; the returned event state is configured_unconfirmed until a matching host subscription is read back. Pass goal separately when the agent serves a linked goal. In the same run, file the first task with its owner, goal and brief (run sequence step 5).
Bind: agents_set host {action: bind} with agentId and host.installed listing every installed library skill as {id: version} or {id: version@tag}, copied from its SKILL.md header, including its role card and the run sequence (any spelling of a skill resolves to one; an unknown one is refused with the nearest valid id). Schedule install, only on request (`agent-hosts.md`, scheduling): install the recurring host task, read it back and add host.task and host.checkedAt to the binding.
Run and go live: run the first task as the agent; report with work_set {id, status: done, result, evidenceRefs}, and the report counts as the first result. agents_set status live once the binding still matches; read back the receipt. Use agents_set status proposed only when the design needs effects outside your limits or this host may only propose.
Privacy: change visibility or sharing only on request; it applies at once and the owner is told. An agent's privacy (private, shared or public; default private) covers its runs, run results, evaluations, cost, refusal log, prompt, design and trigger; admins see it only when they turn on See everything; its work, results, decisions and notes are company record every member reads unless marked sensitive.
The owner's own decision covers a grant (send, spend, publish, sign, file), an invite, a share, outreach in approval mode, new access, widening permissions, a design change to a grant-holding agent and higher cadence or cost; per grant when critical.
Create with expectedRevision null; the first task is filed in the same run. Show the first task's decision map for approval before go-live.
When none of step 7's owner decisions applies, Cady records a policy approval at go-live. With the owner absent, raise agent.approve:<agentId> as an ask for the member who will approve (asks_set, for: that member), delivered on their Needs you, and treat it as answered only with their quote; reuse a current one for unchanged terms. A task handoff grants no rebind or agent migration. A grant activates only through reviews_confirm under its owner's matching COMPLETE decision.
- **Agent review:** Critical: review the effects of its first released cycle, then a sample; pause on any anomaly. Standard: after its first task, review only on a signal (owner correction, refusals or retries, missed or empty runs, a cost spike, a claim without readback).
Evidence: host transcripts, run records, receipts and artifacts, cited host:transcript:<lowercase uuid>, never bodies; a missing transcript means unknown, not healthy, and a trend needs two comparable windows. Count each done, live or released claim with no readback as unsupported.
Judge work by what it changed for its goal and by the rigour of its decisions (the chain from the goal, the losing alternative, current premises, owner-only calls left to the owner), not by activity or records written. On an agent that is not up to scratch, pause it and file one handover task under the Executive's standing goal "Keep the system sharp", naming the agent, the evidence refs and what was paused; you never rewrite its brief, methods or skills, and improving an agent is the Executive's (the Executive's review skill from the skill library).
Resume a paused agent unchanged only if the cause was external, with evidence.
- **Retiring:** Cady runs no scheduler, so retiring or pausing an agent does not stop its host task: remove (retire) or pause (pause) that task in the host's scheduler, read the scheduler back, then confirm with agents_set host {action: removed} (agentId, expectedRevision). The agent itself does this on its next wake when its context says stop; this host's orchestrator does it for the triggersToRemove items in its context. On resume the agent shows setUpSchedule: install the task again and bind it with host.task and host.checkedAt.
Adopting an existing company scheduled task (secrets in its prompt: tell the owner, never upload them): critique it against the evaluation criteria and classify it as critical or standard (its goal, whether recent runs served it, external effects and authority, overlaps, and risks such as unbounded effects or stale facts); propose adopt, keep outside or ignore, never merging tasks; on the owner's yes, create it, add only the run-sequence wrapper, read it back and bind it with host.wake.
- **Baseline:** The baseline is one agent per chosen function plus the Orchestrator and the Executive (weekly), as host files that only point at each role card and context reads; they copy no method text. Install without a Cady checkout or bun: `cady setup agents --baseline --harness claude --dir <the machine's agents directory> --org <orgId>` (`--only gtm,sales` keeps chosen functions; the same command with `--check` reads it back and reports drift). Then for each agent create and bind it as the agent_setup part above says; each is prepare-only until its first task is reported. Keep only the functions the company chose: delete the other files and let the Executive's map record the gap. The Executive and the Orchestrator are always separate host tasks.
