# System map (product map) and dimension maps

**Point:** Give people and agents one short, top-down map of a product: its point, its decisions and where a change goes.

- **Template:** System map format (the product map's format), the same for every product.
Levels: the product, its angles, each angle's key areas (two to five), the subjects (5 to 40 in all), a subject's parts, then the code it owns. Every node has a one-sentence point and its own bets; bets are not a level. The angles for software are Business logic (what it does), Interface (how people and agents reach it), Infrastructure (what it runs on) and QA (how we know it works); for a service or a physical product choose three or four that split it the same way, say so, and keep QA. A subject is something a person would change that has its own reason to exist. Core is the records the product's logic is built on; a module is a system of record that can be left out; a dimension is a part of how it is engineered (an Interface, Infrastructure or QA subject) that owns its code areas and, where a register exists, a register row; a quality is not a subject (`quality-classes.md`). A subject sits in one key area, where a change to it is decided; when paths nest, the longest matching path owns the file.
Bets: a bet is a choice that could have gone another way, kept as `{id, bet, instead_of, why, origin, source}`. Origin is owner (their words and hedges), inferred (from the code or a document) or proposed (yours); source is where the wording came from, and a research pointer goes in the reason. It is rendered `- **<bet>.** Instead of: <option>.`, followed on a card by `Why: <reason>` when one is recorded; origin, and the reasons of product, angle and release bets, are read from the source. A bet with no reason or no alternative stays and is counted as a gap. Never invent a decision; a missing one is a question for the owner. One home per fact: decisions stay decisions, and the map cites them by subject.
Files, in the folder `model` under the repository's `docs` folder: the source `model.json`; the script `render_map.py`; and its outputs `product-map.md` (the front page, then the cards; the file to publish) and `gaps.md`. The source's keys, in the method's normalised form; every record below `product` has id and name: `product` (point, bets); `framework.angles[]` (point, bets, `areas[]` with point and `subjects`, the ids); subject records in `app.core[]`, `app.modules[]` and `dimensions[]`, these with `register_ids` (point, bets, `parts[]` of `{name, point}`, `guarantees[]` of `{text, test}`, `home`: its paths); `loops[]` (point, `nodes`: the subjects it runs through, `watch[]`: its traps as `{when, then, src}`); `releases[]`, ordered, the first current (`by`: who set it and when, point, bets, `items[]` of `{id, text, paths, status}`); `questions[]`, the owner questions. The script derives the rest at each render and stores none of it: file counts, each path's point, tools, Touches, open work and every count.
Front page, under about 10 KB, in this order: `## 1. The point` (the product's point, then the current release goal); `## 2. How it runs, and why it is built this way` (the product's bets, one simple architecture diagram); `## 3. Decision tree` (per angle `**<angle>.** <point>`, `Bets:`, then `Key areas:` with one line per area, `- **<area>:** <point>` and its subjects' names); `## 4. Using this map` (how to find a subject and its card; the code wins, and the map is fixed in the same change); `## 5. State of the map`.
Card, one per subject, titled `## <subject name>` with its sections one level below. Required, in this order (a render may add its own between or after); omit one with nothing to say, never rename it: `**Point:**`; `**Where it sits:**` (angle > key area); `**Size:**` (files, tools, guarantees, bets); What it is made of (its parts); Why it is this way (its bets); Must stay true (each guarantee with `Test: <file>` or `**No test cited.**`); Known traps (when, then, the file to see; on the card owning that file); Read this code (each path with its file count and its point: the file's leading comment or the folder README's first line, else "no point stated"); Its tools (commands or callable operations defined in its own code); Touches (its loops, the subjects on them, the subjects sharing its code); Open work (the releases' items not done whose paths it owns, as `**id** (status): text`; with no tracker or roadmap, say so).
A dimension's Point answers its one question. With a dimension register, Where it sits adds its register ids and its one owner (read from the register, not stored), and its first bet is the label (differentiating or not, with the reason); with none, omit them, and a missing label is an owner question. Journey goals go on the journey subject under QA: Must stay true, one line per goal with its acceptance, in lifecycle order.
State of the map and `gaps.md` give the same derived counts, over card bets: bets with no recorded reason, bets with no "instead of", guarantees citing no test, open items on no card and traps on no card. `gaps.md` adds at most seven owner questions, those blocking a subject's point or a release goal first.
A map in the earlier page shape moves to this format at its next larger change.
- **Sources:** What the map rests on, in both entries: research on Technology and on Users, and an understanding of Assets. Each is owned elsewhere: point to it, do not restate it. Technology is a research concern: the technology research file (research/<title>.md, `cady-product-research`). Users (what problem are we really solving) is half product research (interview syntheses, `cady-product-customer-interview`, and the assumptions `cady-company-evidence` records) and half from GTM and the relationship manager (the persona profile, `cady-gtm-persona-profile`, and what customers said in their relationship records). Cite each as file:<id> in the reason of the bet it supports. Assets (what resources the company has) is an overall company understanding. What bears on the product, such as how much budget there is, comes in as a bet on the product: the limit, with a pointer to the company tree or the budget record. Outside a company record system, cite a repository document as file:<repo path>.
- **Existing project:** Entry 1, an existing project: generate its map from the repository in the template's format. 1. Read before writing: the README and docs, the entry points, the top two levels of folders, the tests, CI, and any decision records or tracker. Copy owner statements word for word with where you found them; when authorship is unknown, quote them in the reason, mark the bet inferred and add one owner question asking which documents are the owner's own. 2. Product: write the point as: does [what] for [whom]; beats [the alternative] on [what]. Then three to seven bets. If the repository does not say whom it is for or what it beats, write your best reading and add an owner question; the point has no origin key. 3. Place the angles and their key areas, each with a point. 4. List the subjects, put each in one key area and name the paths it owns. 5. Fill each subject's record with the "sources" pointers that exist, then write the script and render. 6. Run the part "check".
- **New product:** Entry 2, a new product: write the map before the code, so each short iteration changes named subjects against a stated point. 1. Start from the part "sources": the point from the Users research, the technology bets from the Technology research, the limits from Assets. A bet with nothing behind it is proposed. 2. Do entry 1's steps 2 and 3 from them. 3. Name only the subjects the first release needs, each with its point, bets, guarantees (no test cited until one exists) and the paths it will own. 4. Give the release a goal a user can reach end to end. 5. Build one release at a time. After each, render again, change a point or a bet only when a decision changed, and add the subjects the next release needs.
- **Check:** Checking a map. On every change: every subject is in one key area; every cited path exists or, for a new product, is planned in the current release; the front page and the cards have the template's sections, headings and order. On first generation and on a format change only: (a) Blind use. An agent that has seen neither the code nor the run that wrote the map gets only the map and three real changes (merged changes described without their paths; for a new product, items of the first release) and names for each the subject, the paths to read and what must stay true. The map passes when the answers match where the change landed or is planned; each miss is fixed in the map. (b) Consistency. A second agent running the same entry on the repository produces the same levels, source keys, sections and headings; subject names may differ.
- **Drafting:** Drafting a product map. First find it: the File named <product's node path>/product-map.md (product/product-map.md, or product/<key>/product-map.md for one of several products), found with files_read mode find. If it exists, read it and update the map at its writer instead of starting another. Otherwise find the single writer from the host: the repo for software, else a Notion page or an HTML template you edit. Draft from the template, and review a new map or a larger change before merging, per cady-engineering-independent-review. Publish one Markdown File (export a Notion or HTML writer to Markdown; Files takes no HTML) with `cady product map publish <path> --product <node path> --writer <writer URL>`. The first run uploads the File under that name. Every later run, including the one whoever merges a map change runs from the merged source, adds a version of the same File and keeps the writer. No decision names the map: its name is the pointer, and the File names its writer on its first line.
Keep the map true:
- Make each claim checkable and flag it when false, instead of prose no check reads.
- Mark anything to be removed with the work item that removes it, instead of a bare "to be removed" note.
- **Dimension maps:** Dimension maps. Save a map with files_set as a <slug>.logicmap.json File (format cady.logic-map.v1), then cite its file:<id> as evidence on the node it maps. For a product you build in code, add a development-loop or owner map when the product map leaves a consequential flow unclear.
