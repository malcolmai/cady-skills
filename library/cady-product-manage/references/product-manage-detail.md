# Product first session and run to done

**Point:** Set up the first session and run a goal to a live, measured result.

- **First session:** 3. Minimum first session: (a) if the company has no product, name it: pick a lowercase productId (letters, digits, underscore) and record it with decisions_set, subject product:offering-<productId>, headline exactly "Offering <productId>: <name>" (add "; parent <productId>" for a product inside another, and "; file [file:<id>]" once its description is a File named offering/<productId>.md from files_set with name, purpose, stage, outcome and capabilities); that line is the product scope, and goals, tasks, stories and product:<productId>:<name> decisions must name a defined productId (a company with no product yet may use one key before defining it). (b) Discovery is part of the job: if no customer has spoken yet (no accepted ICP on the tree, no current assumption, no customer evidence in CRM), do not wait or treat a guess as validated. State one assumed ICP (who, circumstance, observable signals) and one problem assumption (the job, current alternative, what they pay in money, time or risk), with what would prove it wrong. Record it as a hypothesis bet with decisions_set (bet.chosen is the assumption in one short sentence; bet.why the job, alternative and what they pay; bet.measure what would prove it wrong; basis hypothesis), evidenceRefs the sources used. Tell the person it is an assumption they can replace. (c) Then one goal record with brief.target under `company-goals.md`, as `cady-company-executive-review` step 13 defines; for a product people use, make it a first-value goal: their first useful result where they meet it, with brief.target.definition saying it is read from a blind walk of one story on the deployed product and next naming who takes that reading and how often. Defer dimensions, maps, other stories, research and module choices until a decision needs them, except on the crux.
- **Run to done:** 11. Run to done (the loop for a goal owner; only f ends it). a) Work the goal's ranked items (step 7) through Engineering and QA. b) Raise each call that stays controversial after testing and review, or owner-only fact, the roadmap needs once in this run, each with options, your recommendation, unlocks and `blocks` naming its own item (run sequence step 5); decide the rest yourself and record it, and build what does not depend on it. c) When no ready item remains, run the `cady-engineering-system-cycle` review against the goal's doneWhen and the dimension register: findings become ranked items and you return to a; only a review with no material finding ends the roadmap, recorded as a checkpoint. d) Release per policy: read policy:release and grant.release:<company> (`cady-company-decision-check` step 2). Under a covering grant, promote through the company's release route yourself; where the policy names who deploys, prepare the exact release (SHA, checks, rollback) and raise one approval ask to that person; with no policy, raise one ask recommending one. Never widen a grant. e) Verify by reading the live target back; cite the deploy receipt and set the release stage (step 8). f) Close the goal: read the target's source (its definition or sourceRef, for example a usage report) and record a reading from it (measure {value, at, sourceRef}); never record a count you did not read. If the release is live, doneWhen holds and the goal's target count is met: the goal call stop {reason: met, evidenceRefs: [review checkpoint, release receipt]}; confirm no OPEN or BLOCKED own items or unresolved effects remain; raise one ask 'Goal <name> is done and live. What next?' with options, and end the run reporting the goal done. The agent is then idle. If the release is live and doneWhen holds but the target count is not yet met: keep the goal open, report the release done, and make driving the target (users, sends, the unit the target counts) the next ranked item; do not stop the goal as met.
