# Product map and dimension maps

**Point:** Give agents one versioned map of how a product works, a File named for its node path, with dimension maps.

- **Template:** Product map template: one File of sections, each a page of the map. Fill it for the product, keep what helps and drop what does not; it is a start, not a form. Each page opens with its point and a bet on how best to do it (`## <page>`, `Point: ...`, `Bet: ...`), then its content. One home per fact: decisions stay decisions, and the map cites them by subject. 1. Point and bets: why the product exists, for whom, and the bets it stands on. 2. Journeys: user outcomes in lifecycle order, each with its acceptance. 3. Architecture: one simple diagram and the owner of each part. 4. Dimensions: each with id, one owner, one question, label (differentiating or not, with reason), the quality classes it crosses when built in code, and the active set. 5. Loops: the recurring loops that keep the product working, each with its trigger and owner. 6. Roadmap: ordered next slices, each citing the journey or dimension it serves. Leave off scope, pricing and ICP (the tree), rules (decisions), findings and status (work).
- **Drafting:** Drafting a product map. First find it: the File named <product's node path>/product-map.md (product/product-map.md, or product/<key>/product-map.md for one of several products), found with files_read mode find. If it exists, read it and update the map at its writer instead of starting another. Otherwise find the single writer from the host: the repo for software, else a Notion page or an HTML template you edit. Draft from the template, and review a new map or a larger change before merging, per cady-engineering-independent-review. Publish one Markdown File (export a Notion or HTML writer to Markdown; Files takes no HTML) with `cady product map publish <path> --product <node path> --writer <writer URL>`. The first run uploads the File under that name. Every later run, including the one whoever merges a map change runs from the merged source, adds a version of the same File and keeps the writer. No decision names the map: its name is the pointer, and the File names its writer on its first line.
Keep the map true:
- Generate every fact the code already knows and hand-write only points, bets and definitions, instead of hand-copying lists, counts, paths and structure.
- Give each fact one home and refer to it by id or path, instead of restating it on several pages.
- Make each claim checkable and flag it when false, instead of prose no check reads.
- Mark anything to be removed with the work item that removes it, instead of a bare "to be removed" note.
- Update the map in the same change as the code, instead of a later pass.
- Keep views, results and history out of the source and render them, instead of committing status tables and change logs into the map.
- Cut a section no agent or reviewer reads when deciding, instead of keeping it because it is true.
- **Dimension maps:** Dimension maps. Save a map with files_set as a <slug>.logicmap.json File (format cady.logic-map.v1), then cite its file:<id> as evidence on the node it maps. For a product you build in code, add a development-loop or owner map when the product map leaves a consequential flow unclear.
