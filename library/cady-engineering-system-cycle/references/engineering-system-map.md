# System map (product map) and dimension maps

**Point:** Give people and agents one short, top-down map of a product: its point, its decisions and where a change goes.

- **Template:** System map format (the product map's format), the same for every product.
Levels: the product, its angles, each angle's key areas (two to five), the subjects (5 to 40 in all), a subject's parts, then the code it owns. The counts are a guide. Every node has a one-sentence point and may have bets; bets are not a level. The angles for software are Business logic (what it does), Interface (how people and agents reach it), Infrastructure (what it runs on) and QA (how we know it works); a service or a physical product takes three or four of its own, with QA kept.
Subjects: a logic subject is a thing the sources or users name; a dimension (an Interface, Infrastructure or QA subject) answers one question, the register's or a usual one (`engineering-cycle-dimensions.md`); neither is cut by folder or size, and a quality is not a subject (`quality-classes.md`). A module is a part a customer can decline or switch off while the product's point still holds; anything else users name is core. A cross-cutting thing sits where its question is: for example, who may do what is Business logic and the sign-in that proves who is calling is Infrastructure.
Bets: a technology bet follows its dimension's label (differentiating or not): the most reliable widely used approach, or for a differentiating dimension the latest that fits the resources. With no label, propose the widely used approach only where the sources show no choice. A proposed bet is marked proposed; never write one as decided; a missing decision is a question for the owner. One home per fact: decisions stay decisions, and the map cites them by subject.
The tool is two files, in this skill's folder or in the Cady skill library (github.com/malcolmai/cady-skills), under `assets/system-map`. `map.schema.json` names and explains every key of the source, and its `home` and `governs` say who owns a path. `render_map.py` checks a source against it and writes `product-map.md` (the file to publish) and `gaps.md`. If you cannot get the two files, stop and say so. Copy both beside the source, `model.json` in the folder `model` under the repository's `docs` folder, and use them unchanged.
An existing map in another shape moves to this format the next time it is restructured.
- **Sources:** What the map rests on: research on Technology and on Users, and an understanding of Assets. Each is owned elsewhere: prefer a pointer to restating it. A pointer goes in the reason of the bet it supports, as file:<id>, or file:<repo path> without Cady. Technology is a research concern: the technology research file (research/<title>.md, `cady-product-research`). Users (what problem are we really solving) is half product research (interview syntheses, `cady-product-customer-interview`, and the assumptions `cady-company-evidence` records) and half from GTM and the relationship manager (the persona profile, `cady-gtm-persona-profile`, and what customers said in their relationship records). Assets (what resources the company has) is an overall company understanding. What bears on the product, such as how much budget there is, comes in as a bet on the product: the limit, with a pointer to the company tree or the budget record. Where the research does not exist, write no stand-in.
- **Build:** Building a map: the same steps for an existing product and a new one. For a new product write the map before the code, so each short iteration changes named subjects against a stated point. Where a step needs what you do not have (Cady, another skill, a second agent, research), do what you can, say in the map's change (the commit or pull request that changes the map) what was not done and why, and add an owner question where the owner must decide.
1. Find the map (the part "Drafting"), copy the tool beside the source, read `map.schema.json` in full, then read the sources. Existing: the README and docs, the entry points, the top two levels of folders, the tests, CI, and any decision records or tracker. New: the Users research (for the point), the Technology research (for the technology bets), the limits from Assets and the brief (what the owner asked for). If the brief is not a file in the repository, save it beside the map. A document the owner gave you as theirs, the brief included, is the owner's, and its sentences stay after clean-up: one that states a choice is copied word for word as the bet, with where you found it as its source; one that only describes goes into the point of the node it is about. A bet from a document that only sits in the repository and names no author is inferred; ask once which documents are the owner's own.
2. Product: its point and its bets. If the sources do not say whom it is for or what it beats, write your best reading and add an owner question.
3. Place the angles and their key areas, each with a point.
4. List the subjects with the paths each owns, and with them their guarantees, their tools, and the loops and traps the sources name. For a new product, name only the subjects the first release needs, one planned folder each, renamed when the code lands.
5. Releases: from the tracker or roadmap, with its ids. With none, write one release as the schema's `releases` says and ask the owner to confirm it. Items are in build order, layer by layer, each what the next reads from: the stored shape, then the logic on it, then what reaches it. The item that writes a part's `schema` file comes before the other items of its subject; the tool checks that, and the order across subjects is yours to keep.
6. Complete `model.json` as the schema says. Stage new files, run `render_map.py` and fix what it refuses. Where the render is committed, add `--no-file-counts`.
7. Clean up (the part "Clean up"), run the part "Check", then review and publish (the part "Drafting"). For a new product, then build the product one release at a time. After each item, render again, change a point or a bet only when a decision changed, and add the subjects the next release needs.
- **Clean up:** Cleaning up, at every build and every update of a map: always clean up if there is anything to clean up, including the codebase's existing documentation and the references to it, so there is one system, if that exists. Look for what the map now holds: architecture and overview documents, older maps, lists of folders, modules or decisions, and every reference to them (links in the README and in agent instructions, links between documents, comments and scripts that name them). The map holds what the front page or a card states, and the first line of a listed path's README or leading comment; finer detail stays. For each one, remove it, or cut it down to what the map does not hold and point it at the map; then fix every reference to it. A document the map does not replace (a decision record, a runbook, an API reference, research) stays. Removing or rewriting a project's documents is a change to that project: make it as a change of its own, through that project's usual review (agent instruction files through their own change path). List there what you removed, what now points at the map and what you kept, with the reason. Where the project states no review path, still make that change and ask the owner to confirm it. Where you may not change the project, remove nothing: give its owner the list and ask them to make or approve it. When there is nothing to clean up, say so in the map's change.
- **Check:** Checking a map. On every change: `render_map.py --check` passes, and clean-up (the part "Clean up") is done. On first generation and on a format change only: blind use. An agent that has seen neither the code nor the run that wrote the map gets only the map and three real changes (merged changes described without their paths; for a new product, or with no merged changes, open items) and names for each the subject, the paths to read and what must stay true. The map passes when the answers match where the change landed or is planned; each miss is fixed in the map. With no second agent, say blind use was not run; never stand in yourself.
- **Drafting:** Drafting a system map. First find it: the File named <product's node path>/product-map.md (product/product-map.md, or product/<key>/product-map.md for one of several products), found with files_read mode find. Without Cady, look in the repository for `model.json` in the folder `model` under `docs`. If a map exists, read it and update it where it is edited instead of starting another. Otherwise ask where it is edited: the repo for software, else a Notion page or an HTML template you edit; with nobody to ask, take the repo and say so. With no repository, make the same folder (`model` under `docs`) among the product's files, keep the source and the tool there, run the tool, and put the rendered `product-map.md` on the page. After the check, review a new map or a larger change before merging, per cady-engineering-independent-review. Then publish one Markdown File (export a Notion or HTML page to Markdown; Files takes no HTML) with `cady product map publish <path> --product <node path> --writer <URL of the place it is edited>` (without either, say it was not done). The first run uploads the File under that name. Every later run, including the one whoever merges a map change runs from the merged source, adds a version of the same File and keeps that place. No decision names the map: its name is the pointer, and the publish command writes where it is edited on its first line.
Keep the map true:
- Make each claim checkable and flag it when false, instead of prose no check reads.
- Mark anything to be removed with the work item that removes it, instead of a bare "to be removed" note.
- **Dimension maps:** Dimension maps. Save a map with files_set as a <slug>.logicmap.json File (format cady.logic-map.v1), then cite its file:<id> as evidence on the node it maps. For a product you build in code, add a development-loop or owner map when the product map leaves a consequential flow unclear.
