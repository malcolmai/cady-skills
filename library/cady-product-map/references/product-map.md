# Product map and dimension maps

**Point:** Give people and agents one short, top-down map of a product: its point, its decisions and where a change goes.

- **Template:** Product map format, the same for every product.
Why the map works this way: it should allow a founder to autonomously build a really strong, quality product. Where no rule covers a case, choose what serves that: each file about one thing, one owner for each file, the stored shape written before the logic on it.
Levels: the product, its angles, each angle's key areas (two to five), the subjects (usually 5 to 40 in all), a subject's parts, then the code it owns. Every node has a one-sentence point and may have bets; bets are not a level. The angles for software are Business logic (what it does), Interface (how people and agents reach it), Infrastructure (what it runs on) and QA (how we know it works); a service or a physical product takes three or four of its own, with QA kept.
Subjects: a logic subject (a feature) is a thing the sources or users name; a dimension (an Interface, Infrastructure or QA subject) answers one question, the register's or a usual one (`engineering-cycle-dimensions.md`); neither is cut by folder or size, and a quality is not a subject (`quality-classes.md`). A module is a part a customer can decline or switch off while the product's point still holds; anything else users name is core. A cross-cutting thing sits where its question is: for example, who may do what is Business logic and the sign-in that proves who is calling is Infrastructure.
One owner per file: a file that needs two owners is split, as the schema's `splits` says. Moves and splits follow the part "Clean up".
Bets: a technology bet follows its dimension's label (differentiating or not): the most reliable widely used approach, or for a differentiating dimension the latest that fits the resources. With no label, propose the widely used approach only where the sources show no choice. A proposed bet is marked proposed; never write one as decided; a missing decision is a question for the owner. One home per fact: decisions stay decisions, and the map cites them by subject.
The tool is two files, in this skill's folder or in the Cady skill library (github.com/malcolmai/cady-skills), under `assets/product-map`. `map.schema.json` names and explains every key of the source, and its `home` and `governs` say who owns a path. `render_map.py` checks a source against it and writes `product-map.md` (the file to publish) and `gaps.md`. If you cannot get the two files, stop and say so. Copy both beside the source, `model.json` in the folder `model` under the repository's `docs` folder, and use them unchanged.
An existing map in another shape moves to this format the next time it is restructured.
- **Sources:** What the map rests on: research on Technology and on Users, and an understanding of Assets. Each is owned elsewhere: prefer a pointer to restating it. A pointer goes in the reason of the bet it supports, as file:<id>, or file:<repo path> without Cady. Technology is a research concern: the technology research file (research/<title>.md, `cady-product-research`). Users (what problem are we really solving) is half product research (interview syntheses, `cady-product-customer-interview`, and the assumptions `cady-company-evidence` records) and half from GTM and the relationship manager (the persona profile, `cady-gtm-persona-profile`, and what customers said in their relationship records). Assets (what resources the company has) is an overall company understanding. What bears on the product, such as how much budget there is, comes in as a bet on the product: the limit, with a pointer to the company tree or the budget record. Where the research does not exist, write no stand-in.
- **Build:** Building a map: the same steps for an existing product and a new one. For a new product write the map before the code, so each short iteration changes named subjects against a stated point. Where a step needs what you do not have (Cady, another skill, a second agent, research), do what you can, say in the map's change (the commit or pull request that changes the map) what was not done and why, and add an owner question where the owner must decide.
1. Find the map (the part "Drafting"), copy the tool beside the source, read `map.schema.json` in full, then read the sources. Existing: the README and docs, the entry points, the top two levels of folders, the tests, CI, and any decision records or tracker. New: the Users research (for the point), the Technology research (for the technology bets), the limits from Assets and the brief (what the owner asked for). If the brief is not a file in the repository, save it beside the map. A document the owner gave you as theirs, the brief included, is the owner's, and its sentences stay after clean-up; the schema's `bet`, `origin` and `source` say how each is written.
2. Product: its point and its bets. If the sources do not say whom it is for or what it beats, write your best reading and add an owner question.
3. Place the angles and their key areas, each with a point.
4. List the subjects with the paths each owns, and with them their guarantees, their tools, and the loops and traps the sources name. Organise by feature: a feature owns everything that exists only for it (its rules, stored data, screens, request handlers, tests); shared code (what a dimension owns) knows no product rule and imports no feature; a feature uses another only through its entry (the files it exports for others). The entry or assembly that wires features together (a server's API entry; Cady's `apps/`) is not shared code. A feature subject's `home` is one folder, plus the paths a layer rule or a shared test folder keeps elsewhere (Cady keeps direct database access under `platform/data/stores/<feature>/`): each is that feature's part, not a second owner. A feature publishes through its entry file; a lazy entry only where the eager one would grow what a client must load. A port (an interface filled at assembly) is wanted in two cases only: an outside provider (one adapter per provider), or a lower layer calling code a higher layer owns; never between two parts of the same layer, never to dodge an import rule. For a new product, name only the subjects the first release needs, one planned folder each; correct the path if the code lands elsewhere.
5. Releases: from the tracker or roadmap, with its ids. With none, write one release as the schema's `releases` says and ask the owner to confirm it. Items are in build order, layer by layer, as the schema's `items` says; the tool checks that a part's `schema` item comes first in its subject.
6. Stage new files, run `render_map.py` and fix what it refuses. Where the render is committed, add `--no-file-counts`.
7. Clean up (the part "Clean up"), run the part "Check", then review and publish (the part "Drafting"). For a new product, then build the product one release at a time. After each item, render again, change a point or a bet only when a decision changed, and add the subjects the next release needs.
- **Clean up:** Cleaning up, at every build and every update of a map: always clean up if there is anything to clean up, including the codebase's existing documentation and the references to it, so there is one system, if that exists. Look for what the map now holds: architecture and overview documents, older maps, lists of folders, modules or decisions, and every reference to them (links in the README and in agent instructions, links between documents, comments and scripts that name them). The map holds what the front page or a card states, and the first line of a listed path's README or leading comment; finer detail stays. For each one, remove it, or cut it down to what the map does not hold and point it at the map; then fix every reference to it. A document the map does not replace (a decision record, a runbook, an API reference, research) stays. Removing or rewriting a project's documents is a change to that project: make it as a change of its own, through that project's usual review (agent instruction files through their own change path). List there what you removed, what now points at the map and what you kept, with the reason. Where the project states no review path, still make that change and ask the owner to confirm it. Where you may not change the project, remove nothing: give its owner the list and ask them to make or approve it. Clean up how the code is organised too. Six tests show poor organisation: one idea in many places; one file doing two jobs; shared code that knows the product; reaching inside another feature; no owner or two owners; a feature you cannot delete by removing the paths its `home` names. What to look at: the same rule or constant in two files; a file whose first line names two things; a dimension's file that imports a feature or names its records; an import of a file inside another feature's folder other than its entry; a code file `gaps.md` lists as unowned (the files the schema expects unowned are fine); a file outside a feature's `home` that exists only for it. On an update, apply the tests only to the subjects the change touches. A move fixes only a file in the wrong folder; an import that reaches inside another feature is fixed by importing its entry, when the entry already exports it. Make a move the simple reliable way: move whole files, keep behaviour, and change only import lines. One idea in many places and shared code that knows the product are always items; a file doing two jobs is split as the schema's `splits` says. Write an item instead of a move when the move would weaken an isolation or audit boundary (for example where direct database access is allowed) or create an import cycle, when no check you ran would catch a broken move, when anything but imports names the file by path, or when it touches what `splits` always makes an item. A move left as an item is an open item in the current release, its `text` naming the files and the folder they go to, both in `paths`. Make the moves one reviewable change of their own, before the map's, and write the rest as items. Stop when no test finds a whole-file move left to make. When there is nothing to clean up, say so in the map's change.
- **Check:** Checking a map. On every change: `render_map.py --check` passes, and clean-up (the part "Clean up") is done. On first generation and on a format change only: blind use. An agent that has seen neither the code nor the run that wrote the map gets only the map and three real changes (merged changes described without their paths; for a new product, or with no merged changes, open items) and names for each the subject, the paths to read and what must stay true. The map passes when the answers match where the change landed or is planned; each miss is fixed in the map. With no second agent, say blind use was not run; never stand in yourself.
- **Drafting:** Drafting a product map. First find it: the File named <product's node path>/product-map.json (product/product-map.json, or product/<key>/product-map.json for one of several products), found with files_read mode find; a product-map.md File beside it is an earlier form and stale. Without Cady, look in the repository for `model.json` in the folder `model` under `docs`. If a map exists, read it and update it where it is edited instead of starting another. Otherwise ask where it is edited: the repo for software, else a Notion page or an HTML template you edit; with nobody to ask, take the repo and say so. With no repository, make the same folder (`model` under `docs`) among the product's files, keep the source and the tool there, run the tool, and put the rendered `product-map.md` on the page. After the check, review a new map or a larger change before merging, per cady-engineering-independent-review. Then render the packet with `render_map.py --packet` and publish it, the JSON packet and never the Markdown, with `cady product map publish product-map.json --product <node path> --writer <URL of the place it is edited>` (without either, say it was not done). The first run uploads the File under that name. Every later run, including the one whoever merges a map change runs from the merged source, adds a version of the same File and keeps that place. No decision names the map: its name is the pointer, and the packet says where it is edited (`rendered.writer`).
Keep the map true:
- Make each claim checkable and flag it when false, instead of prose no check reads.
- Mark anything to be removed with the work item that removes it, instead of a bare "to be removed" note.
- **Dimension maps:** Dimension maps. Save a map with files_set as a <slug>.logicmap.json File (format cady.logic-map.v1), then cite its file:<id> as evidence on the node it maps. For a product you build in code, add a development-loop or owner map when the product map leaves a consequential flow unclear.
