# Chosen connector reads and CRM update

## Integrations

- **Auth handoff:** Use the provider's supported consent/pairing flow and explain the exact UI entry point. For QR flows, identify the scanner intended for that operation. Show the current code or actionable handoff in the final user-visible response while its bounded pairing process remains alive; never persist QR payloads, codes or credentials in company records. Inspect sanitized terminal events and auth postconditions, then the user's actual screen/error before diagnosing incompatibility. Stop and surface unsupported security ceremonies rather than rotating unusable codes. Clean up only task-owned pairing processes/artifacts after completion or expiry.
- **Conversation jobs:** For relationship work, qualify three distinct host operations against the selected chat provider and CRM: (1) list bounded chat snippets with exact account/thread IDs, source timestamps and coverage, then resolve each participant in the selected CRM as new_in_checked_scope, matched with useful metadata, explicitly not relevant, or ambiguous; explicit exclusion needs a user/CRM-owned source and reason, never an inferred nonmatch; (2) read one exact thread since a successfully processed checkpoint or, on request, its available full history, distinguishing no new messages from partial/stale coverage, and upsert observed activities with source IDs before advancing the checkpoint; (3) send to the exact thread/recipient only under the delivery owner's authority controls, preserve the provider result, then read back delivery and the corresponding CRM activity. Reconcile uncertainty before retry; CRM logging failure does not negate a confirmed send. An adapter may combine steps when its native surface supports them; missing operation or CRM write support is a reported capability gap, never inferred success. Cady CRM is one optional destination, not a required intermediary; its current exact chat-message admission covers LinkedIn.
- **Coverage:** Exercise the actual use-case sequence and distinct operations, including alternate methods only when relevant; read success does not qualify writes, and a direct message does not qualify invitations or other message routes. For sequences, include delay/resume, stop-on-reply or cancellation and duplicate prevention where applicable. Cover relevant risk_first failures with safe fakes or sandbox fault injection before live work; do not induce harmful production effects. Qualify the tested account, tool/version, method and workflow only; changes require proportionate rechecks. Separate local, sandbox and live evidence; a few successful cases never establish unattended reliability.
- **Efficiency:** Reuse relevant company context, source IDs and valid tool descriptions within the task; discover only missing capabilities and refresh when account, scope, version or availability changes. Start with metadata, provider filters, field selection and a bounded page; fetch bodies or linked resources only when they can change the outcome. Stop when evidence suffices, while stating unexamined coverage; exhaust pagination only when completeness is required. Avoid repeated empty searches without a new signal. Batch or parallelize independent reads within provider limits; serialize dependent effects. For large results, use host-side code to filter, join and aggregate structured data before returning concise evidence to the model. Preserve source IDs, freshness, errors and coverage when reducing output. Optimize total calls, tokens, latency and repair cost, not just call count; do not sacrifice a required verification read.
- **Read path:** Start from the specific business question. Query the smallest useful source scope using exact resource/thread IDs and bounded context. Prefer local read-only structured queries when an existing cache is sufficiently fresh; otherwise use the provider's supported filtered reads or incremental changes. Check missing ranges, pagination and deletions before claiming completeness. A returned page or local row count is not full history. Admit only material decisions, facts, commitments and necessary evidence references to Cady; a host cache is not company-shared authority.
- **Readiness:** Report observed facts separately: installed version; selected account and granted scope; local authentication; current live connection; source coverage/freshness; supported read/write operations; and verified effect receipts. Neither a zero exit code, stored credential, newest-message timestamp nor successful read proves complete sync, a healthy live connection or write capability. Check postconditions and documented terminal events, including storage-cap stops and revoked sessions. An idle quiet account is not necessarily disconnected. Keep volatile readiness out of durable tool preferences; carry only a necessary dated checkpoint with its limits.
- **Relationship records:** For interaction-to-CRM work, use the selected CRM's supported identity and activity surfaces. Resolve people/companies by stable provider IDs and verified contact identifiers before names; stop ambiguous matches. Keep identity/contact facts, dated source messages or notes, relationship summaries, next actions and draft state distinct. Key each activity by source account plus stable message/event ID, keeping thread ID, occurrence time apart from capture time, direction, coverage and source link; preserve corrections and deletions. Link activities and evidence to the exact destination person/company. A bio or unlinked file is not an activity history; do not invent a meeting to fit a missing note endpoint. Label inferred summaries and retain their evidence; update a current summary without overwriting the source history. Verify the record in the destination's actual profile/history view as well as its API, including filters and visibility. Missing activity-write or association capabilities are a concrete integration gap, not permission to change the data model or use an unrelated endpoint.
- **Sync policy:** Separate bootstrap, on-demand refresh, historical backfill and continuous capture; setup does not silently enable all four. Choose cadence from the required freshness and source capabilities, not a universal poll interval. Prefer provider delta cursors or events where available; persist checkpoints only after durable processing, deduplicate stable source IDs, and reconcile missed/expired cursors or best-effort events before claiming coverage. Use one coordinated writer per account/store where the tool requires it, with local readers; use a long-lived sync only when authorized latency/volume justifies it. Define source scope, retention, private storage, optional media, per-run runtime/call limits, cumulative row/disk limits, reconnect budget and cap behavior separately. A total-row cap is not a per-run allowance or rolling retention; when full, stop/report incomplete coverage rather than silently purge or loop. Bound the whole command because an idle timeout can run forever on a busy account. Respect provider deletion/disappearing-message semantics; never invent archival permission.
