# Blockers

A blocker stops progress without being an external risk: a missing or unauthenticated tool, a stale document, an ambiguous specification, a failing check, an empty helper result. Work around it and record the route: the next strongest native path or a script; the reading a careful colleague would take; the cause of a failing check, never its assertion; one new prompt to an empty helper, then one fresh helper of the same class; do only a small remainder yourself, and record any move to a stronger class as an exception. An unauthenticated connection is a blocked capability, not a reason to use another environment or account. Never work around an authorisation wall, a denied permission, a provider challenge or a safety refusal; those stop that channel while the rest of the work finishes. For a product or method defect found during an authorized outcome, record expected versus observed behavior with exact evidence in the existing task or claim and route bounded repair to the owner of that product or method under current authority. Verify the repair, then continue the original operation through its supported owner transition; if none exists, hold an exact actionable handoff. A code fix alone does not complete that outcome. Keep unrelated work moving, and preserve access/provider holds, uncertain-effect reconciliation and review/release gates.
