# Reporting a run

- **Exceptions:** For offline_evaluation or spotcheck only, record through manage_company_agent mode='record_run' using the current schema retrieved through find_cady_tools (tool: manage_company_agent, detail: schema). Preserve requestId, scenarioId, repetition, configurationRef, the Projects-derived evaluation runId, and actual output or outputRef; include only actually observed traces or usage in that schema. Evaluation reporting is exceptional and does not add a second ordinary run write. Do not add scheduled-slot or effect-receipt facts.
- **Output:** Name the requested useful outcome in the task title, not a session or implementation step. First result sentence is the outcome title (what changed, short; the resultSummary field of report_company_work sets the rule) and states whether the requested outcome or only a named milestone is complete; put material remainder up front. Done only when the requested finish line is met; a meaningful completed milestone stays partial on the same work with remainder and nextAction. Session end or intermediate deploy is not completion. A requested release includes applicable tests/QA and verified authorized release; research or drafting is done at the requested usable artifact. Follow with concise checks/limitations and owner artifact or receipt refs. File only what someone will reopen to use or check: a deliverable, or source evidence no owner record holds. Do not file process notes, local transcripts or repeated company context. Use a review packet only when the owner must approve exact materials together; otherwise keep any necessary memo brief and action-led. Local transcript review can diagnose retries, waste, missed instructions, tool misuse and behavior; persist only the material finding, evidence reference and correction in the existing owner.
- **Recovery:** For existing work, supply the expectedRevision read with your intent unless the owner binds the request to your valid claim. Establish decisionId/nonce and a stable partKey for every member of each populated part array before the first mutation; retain them and the unchanged payload after a lost response. A corrected payload gets a new report identity; never refresh a revision to force stale intent. Preserve material checkpoints/no-change, partial/blocked status, unresolved effects and follow the close tool's parts and pre-close checks during recovery.
- **Shape:** The ordinary reporting action is one report_company_work call. Each item carries claim, resultSummary, evidenceRefs when available and nextAction only when needed: one line; narrative goes in the result. A no-work execution is still a run and includes its observed times; a one-off with nothing material to report creates neither a run nor a task. For a continuing responsibility, omit an unchanged no-change result item; ending this run never completes the responsibility. If a linked material result changes the goal's supported summary or next action, reconcile that goal through its current owner and verify the next context; unchanged wakes and completed-task counts do not establish goal progress. Do not separately record the same run. Run metadata is optional: through this same close call, include observed start/end times, usage or output only when the host actually observed them and the owner schema supports them; omit unavailable facts. On a host with a shell and the Cady CLI, run `cady usage read --host <codex|claude-code> --session <current session when known> --started-at <run start ISO>` at close and report usage only when `cady usage read` exits 0; otherwise omit run.usage. Never reconstruct missing usage. If the host provides no clock, register start at the beginning of the real attempt and finish when ending; these are attempt times, not effort duration. Never infer usage, execution start or skill use from a completion time or published version; identify only a skill version actually used. Point to the owner artifact by evidence ref; never duplicate its body in report metadata.
