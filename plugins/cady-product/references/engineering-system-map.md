# Product map template and drafting

**Point:** Give agents one versioned map of how a product works, written once and found from the product's Offering line.

- **Template:** Product map template: one File of sections, each a page of the map. Fill it for the product, keep what helps and drop what does not; it is a start, not a form. Each page opens with its point and a bet on how best to do it (`## <page>`, `Point: ...`, `Bet: ...`), then its content. One home per fact: decisions stay decisions, and the map cites them by subject. 1. Point and bets: why the product exists, for whom, and the bets it stands on. 2. Journeys: user outcomes in lifecycle order, each with its acceptance. 3. Architecture: one simple diagram and the owner of each part. 4. Dimensions: each with id, one owner, one question, label (differentiating or not, with reason), the quality classes it crosses when built in code, and the active set. 5. Loops: the recurring loops that keep the product working, each with its trigger and owner. 6. Roadmap: ordered next slices, each citing the journey or dimension it serves. Leave off scope, pricing and ICP (direction), rules (decisions), findings and status (work).
- **Drafting:** Drafting a product map. First find it: product-area context serves `Product map (<key>): file:<id>`, or read cady_read decision:product:offering-<key> (the product's Offering line) and its `map [file:<id>]` clause. If it names a File, read it and update the map at its writer instead of starting another. Otherwise find the single writer from the host: the repo for software, else a Notion page or an HTML template you edit. Draft from the template, and review a new map or a larger change before merging, per cady-engineering-independent-review. Publish one Markdown File (export a Notion or HTML writer to Markdown; Files takes no HTML) with `cady product map publish <path> --product <key> --writer <writer URL>`. The first run uploads it and records the Offering line with its map clause, or raises one ask when a person must accept that line. Every later run, including the one whoever merges a map change runs from the merged source, adds a version of the same File, keeps the writer and records no decision. The Offering line holds the pointer; the File holds the map and names its writer on its first line.
